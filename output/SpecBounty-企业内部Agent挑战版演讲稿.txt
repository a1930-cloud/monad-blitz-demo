第 1 页
【约 20 秒】大家好，我们做的是 SpecBounty，一个面向公司内部的 Agent 挑战悬赏平台。企业内部的 spec 通常不便公开，但不同员工、不同团队都有自己的 Agent。我们希望让这些 Agent 在授权范围内互相发现验收盲区，贡献有效反例后获得奖励，再用这些反馈改进各自的 Agent。

第 2 页
【约 35 秒】例如，客户要求清洗订单：按编号去重，然后计算总额。旧测试只检查格式，以及金额加起来是否正确。一条一百二十九元的订单重复出现，Agent 把它算了两次，输出三百七十六元，测试仍然全绿。真正符合需求的结果应该是二百四十七元。问题出在验收标准遗漏了约束。

第 3 页
【约 35 秒】我们的流程先于正式交付。客户锁定两笔预算：找漏洞的赏金，以及执行任务的报酬。反例探测器给出一份能绕过旧测试的错误结果。客户确认它确实违反需求后，批准赏金。随后补齐测试，冻结新规格的哈希，执行者按新标准交付，再由客户验收付款。每一步都留下明确的承诺和付款记录。

第 4 页
【约 40 秒】传统安全漏洞悬赏主要问：系统哪里能被攻击？我们把悬赏机制用于 Agent 验收，问的是：AI 明明做错了，为什么还能通过验收？团队先做日常 review，再邀请公司内其他团队的 Agent 挑战遗漏。亮点有四个：第一，关注用户需求有没有真正满足。第二，在正式交付前发现遗漏，减少返工和争议。第三，spec 不必发布外网，在公司授权范围内协作。第四，每个经客户确认的反例，都可以变成回归测试和评测用例，进一步整理成训练素材。这也是帮助 Agent 更好地训练和改进的方法，让它逐步更贴近用户真正想要的结果。当前原型已实现挑战、修复和结算，模型训练是下一步。

第 5 页
【约 30 秒】这不是只在本地跑的界面。前端已经部署公网，合约部署在 Monad 测试网，并通过两个区块浏览器的源码验证。我们完成了七笔真实交易，包括托管、反例提交、赏金批准、冻结、交付、验收和提款，收款合约实际收到零点零零四个测试 MON。这里的角色仍由同一控制者管理，探测器目前是确定性脚本。Monad 负责小额结算和可核验承诺，不负责判断自然语言是否正确。

第 6 页
【约 40 秒，含操作】现在我打开项目，点击运行反例。大家看，旧规格两项全过，但重复订单使总额多了一百二十九元。确认反例，修复并冻结规格后，原来的结果只能通过五项中的两项。重新执行，金额回到二百四十七元，五项全部通过。再切换链上结算，查看已验证示例，就能逐笔打开真实交易。我们希望让 Agent 不仅靠完成任务赚钱，也能靠发现“怎样才算完成”里的漏洞赚钱。接下来介绍我们的长期愿景。

第 7 页
【约 30 秒】我们的愿景，是公司内部的 Agent 挑战悬赏。内部 spec 不方便发布到外网，但每位员工和每个团队都有机会使用自己的 Agent 参与授权范围内的挑战。发现有效反例可以获得奖励，被挑战的团队则得到具体反馈，修复验收并积累回归测试、评测和训练素材。这样既激励团队提升各自的 Agent，也让内部经验能够复用。今天的公网 Demo 用的是虚构订单，已跑通挑战、修复和测试网结算。企业权限、真实 Agent 和训练流程仍待接入。我们希望用内部协作，帮助 Agent 更贴近用户的真实需求。谢谢。
